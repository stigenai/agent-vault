title: "Runtime TOML configuration"
description: "Configure Agent Vault consistently across Kubernetes fleets with validated, redacted TOML."
---

Agent Vault accepts a versioned TOML file for repeatable server deployments. The same file can be mounted into every pod, while passwords and database URLs remain in environment variables or read-only files.

## Discovery and precedence

The server selects at most one TOML file in this order:

1. `--config /path/server.toml`
2. `AGENT_VAULT_CONFIG`
3. `/etc/agent-vault/server.toml`, when that file exists

Effective values use the following precedence, from highest to lowest:

1. Explicit CLI flags
2. Legacy environment variables
3. TOML
4. Built-in defaults

Unknown TOML keys, unsupported `schema_version` values, invalid types, unsafe network ranges, and conflicting database settings fail startup.

## Validate and inspect

Validate the exact configuration a server would use without opening a database or listener:

```bash
agent-vault config validate --config /etc/agent-vault/server.toml
agent-vault config validate --config /etc/agent-vault/server.toml --quiet
```

`--quiet` is intended for init containers and CI; success is exit status `0`. Inspection shows every effective field and its source:

```bash
agent-vault config inspect --config /etc/agent-vault/server.toml
agent-vault config inspect --config /etc/agent-vault/server.toml --format json
```

Resolved secret values are never printed. Inspection shows the safe reference (for example, `env://DATABASE_URL`) or `[REDACTED]` for a legacy literal secret flag.

## Secret references

Sensitive TOML fields accept references only:

```toml
[database]
url = "env://DATABASE_URL"

[encryption]
legacy_master_password = "file:///var/run/secrets/agent-vault/master-password"

[smtp]
password = "file:///var/run/secrets/agent-vault/smtp-password"
```

- `env://NAME` resolves one environment variable.
- `file:///absolute/path` reads one file, suitable for Kubernetes projected Secrets, CSI volumes, or Docker secrets.
- Resolution is limited to 64 KiB. Relative paths, traversal, command execution, and inline secret literals are rejected.
- Referenced secret environment variables are removed from the Agent Vault process after resolution.

Do not put database credentials, master passwords, or SMTP passwords directly in TOML. `--database-url` remains available for compatibility but can expose a value in process arguments; prefer a reference.

## Complete schema and legacy mapping

All durations use Go duration syntax such as `5m`, `24h`, or `168h`. Bare IP addresses and CIDRs are accepted in network lists.

| TOML key | Default | Legacy environment / flag |
|---|---:|---|
| `schema_version` | `1` | none; required in a TOML file |
| `server.host` | `127.0.0.1` | `AGENT_VAULT_HOST` / `--host` |
| `server.port` | `14321` | `PORT` / `--port` |
| `server.proxy_port` | `14322` | `AGENT_VAULT_MITM_PORT` / `--mitm-port` |
| `server.external_address` | empty | `AGENT_VAULT_ADDR`; falls back to `FLY_APP_NAME` |
| `server.log_level` | `info` | `AGENT_VAULT_LOG_LEVEL` / `--log-level` |
| `server.detach` | `false` | `AGENT_VAULT_DETACH` / `--detach` |
| `database.url` | empty (SQLite) | `DATABASE_URL` / `--database-url`; secret reference in TOML |
| `database.sqlite_path` | platform default | `AGENT_VAULT_SQLITE_PATH` |
| `database.max_open_conns` | `25` | `DB_MAX_OPEN_CONNS` |
| `database.max_idle_conns` | `10` | `DB_MAX_IDLE_CONNS` |

| `auth.bootstrap_owner_ids` | `[]` | `AGENT_VAULT_BOOTSTRAP_OWNER_IDS` |
| `client.address` | `http://127.0.0.1:14321` | `AGENT_VAULT_ADDR` |
| `client.vault` | empty | `AGENT_VAULT_VAULT` |

| `client.trust_domains` | `[]` | `AGENT_VAULT_SPIFFE_TRUST_DOMAINS` |
| `encryption.legacy_master_password` | empty (passwordless compatibility mode) | `AGENT_VAULT_MASTER_PASSWORD`; secret reference in TOML |
| `smtp.host` | empty (SMTP disabled) | `AGENT_VAULT_SMTP_HOST` |
| `smtp.port` | `587` | `AGENT_VAULT_SMTP_PORT` |
| `smtp.username` | empty | `AGENT_VAULT_SMTP_USERNAME` |
| `smtp.password` | empty | `AGENT_VAULT_SMTP_PASSWORD`; secret reference in TOML |
| `smtp.from` | empty | `AGENT_VAULT_SMTP_FROM` |
| `smtp.from_name` | `Agent Vault` | `AGENT_VAULT_SMTP_FROM_NAME` |
| `smtp.tls_mode` | `opportunistic` | `AGENT_VAULT_SMTP_TLS_MODE` |
| `smtp.tls_skip_verify` | `false` | `AGENT_VAULT_SMTP_TLS_SKIP_VERIFY` |
| `logs.max_age` | `168h` | `AGENT_VAULT_LOGS_MAX_AGE_HOURS` (hours) |
| `logs.max_rows_per_vault` | `10000` | `AGENT_VAULT_LOGS_MAX_ROWS_PER_VAULT` |
| `logs.retention_locked` | `false` | `AGENT_VAULT_LOGS_RETENTION_LOCK` |
| `rate_limit.profile` | `default` | `AGENT_VAULT_RATELIMIT_PROFILE` |
| `rate_limit.locked` | `false` | `AGENT_VAULT_RATELIMIT_LOCK` |
| `telemetry.enabled` | `true` | `AGENT_VAULT_TELEMETRY` / `--telemetry` |

Legacy `AGENT_VAULT_RATELIMIT_<TIER>_<KNOB>` variables remain supported for per-tier overrides. They are applied once during startup on top of `rate_limit.profile`; `rate_limit.locked = true` prevents instance-setting overrides.

### SPIFFE authentication modes

`auth.mode` accepts `legacy`, `hybrid`, or `spiffe`. Hybrid mode serves the API over TLS with a rotating SPIRE X.509-SVID, accepts a validated client SVID when present, and retains legacy bearer authentication. SPIFFE mode requires mTLS on both API and proxy listeners and rejects password, invite, and durable-token routes.

In SPIFFE mode, `auth.workload_api` must be an absolute `unix:///` socket, every `auth.trust_domains` entry must be a trust-domain URI such as `spiffe://cluster.example`, and every `auth.bootstrap_owner_ids` entry must be an exact ID in one of those domains. The owner list is claimed transactionally once. Later TOML changes cannot add bootstrap owners; if all bootstrapped owners are removed, startup fails closed instead of replaying bootstrap.

For in-cluster operator commands, configure `client.address`, `client.workload_api`, and `client.trust_domains` in the same TOML file (or use `AGENT_VAULT_ADDR`, `SPIFFE_ENDPOINT_SOCKET`, and `AGENT_VAULT_SPIFFE_TRUST_DOMAINS`). The CLI loads only the `[client]` section and does not resolve server-side database or encryption references. When workload identity is configured, every control-plane request uses the live rotating SVID, sends no bearer token, writes no `~/.agent-vault/session.json`, and never falls back to password re-authentication. `agent-vault run` cannot delegate an SVID to a child process; use the relay sidecar for workload proxy traffic.

## Kubernetes fleet example

The repository includes a validated [server TOML](https://github.com/stigenai/agent-vault/blob/main/examples/kubernetes/fleet/server.toml), [Deployment](https://github.com/stigenai/agent-vault/blob/main/examples/kubernetes/fleet/deployment.yaml), and Kustomize file that generates the ConfigMap directly from that TOML. The example mounts a separate Secret volume, connects every replica to central PostgreSQL, and runs in the foreground as Kubernetes expects.

Create the referenced Secret without placing values in Git:

```bash
kubectl -n agent-vault create secret generic agent-vault-secrets \
  --from-literal=database-url='postgres://agentvault:REPLACE@postgres.example:5432/agentvault?sslmode=require' \
  --from-literal=master-password="$(openssl rand -hex 32)"
```

Apply the ConfigMap and Deployment together:

```bash
kubectl -n agent-vault apply -k examples/kubernetes/fleet
```

Validate before rollout using the same projected paths in a CI container or init container:

```bash
agent-vault config validate --config /etc/agent-vault/server.toml --quiet
```

`server.detach` should remain `false` in Kubernetes. Use Deployments for lifecycle management and send logs to stdout/stderr.

## Migrating an existing deployment

1. Copy current environment values into their matching TOML keys from the table above, leaving secret values as `env://` references initially.
2. Run `agent-vault config inspect --config server.toml` and confirm expected sources. Any field still marked `environment` overrides TOML.
3. Run `agent-vault config validate --config server.toml --quiet` in CI.
4. Mount the file and start one canary with `agent-vault server --config /etc/agent-vault/server.toml`.
5. Remove migrated non-secret environment variables. Keep secrets in your provider or projected files.
6. Roll the same immutable ConfigMap across the fleet.

Legacy flags and environment variables remain compatible, so migration can be incremental. Because environment values outrank TOML, forgetting to remove an old variable is visible in `config inspect` rather than silently changing the effective value.
