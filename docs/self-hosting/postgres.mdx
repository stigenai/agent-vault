## Overview

Agent Vault uses an embedded SQLite database by default. Use PostgreSQL when several Agent Vault replicas need central, highly available storage.

Every replica connects to the same database and remains stateless. The database stores the shared encrypted CA state, wrapped encryption keys, policies, and service configuration. PostgreSQL advisory locks serialize schema migration and other cluster-wide coordination. The API can sit behind an L7 load balancer; the MITM proxy requires L4 TCP passthrough.

## Prerequisites

- PostgreSQL 13 or later. The compatibility matrix continuously tests majors 13 through 18.
- A dedicated database and non-administrative login role for Agent Vault.
- A PostgreSQL server CA bundle mounted in every replica.
- A connection budget that accounts for every replica and leaves capacity for migrations, operators, monitoring, and failover.

## Create a least-privilege runtime role

Run provisioning statements with a separate provider or cluster administrator identity. Do not give the resulting Agent Vault login cluster-administration capabilities.

```sql
CREATE ROLE agentvault
  LOGIN
  PASSWORD 'replace-through-your-secret-manager'
  NOSUPERUSER
  NOCREATEDB
  NOCREATEROLE
  NOINHERIT
  NOREPLICATION
  NOBYPASSRLS;

CREATE DATABASE agentvault OWNER agentvault;
```

Connect to the new database as the provisioning identity and give the runtime role an isolated schema:

```sql
REVOKE ALL ON DATABASE agentvault FROM PUBLIC;
GRANT CONNECT, TEMPORARY ON DATABASE agentvault TO agentvault;

CREATE SCHEMA agent_vault AUTHORIZATION agentvault;
REVOKE ALL ON SCHEMA public FROM PUBLIC;
ALTER ROLE agentvault IN DATABASE agentvault
  SET search_path = agent_vault, pg_catalog;
```

Agent Vault runs forward-only schema migrations at startup, so its runtime role must own its database objects and have DDL rights in `agent_vault`. It does not need `SUPERUSER`, `CREATEDB`, `CREATEROLE`, replication, bypass-RLS, or access to other databases. Keep the provisioning identity out of `DATABASE_URL`.

Managed services may require equivalent console or provider-specific commands. The invariant is that the runtime role owns only the dedicated Agent Vault database/schema and is not a cluster administrator.

## Configure verified TLS

For fleet TOML, keep the database URL in a Secret and make TLS policy explicit:

```toml
[database]
url = "file:///var/run/secrets/agent-vault/database-url"
tls_mode = "verify-full"
tls_root_cert = "/var/run/secrets/agent-vault/postgres-ca.crt"
connect_timeout = "10s"
max_open_conns = 25
max_idle_conns = 10
conn_max_lifetime = "5m"
```

The URL should not duplicate `sslmode` or `sslrootcert`; conflicting URL and TOML values fail startup. `verify-full` validates both the certificate chain and the database hostname. `require` encrypts traffic but does not provide the same server-identity guarantee and is not the production recommendation.

The legacy environment equivalents are `DB_TLS_MODE`, `DB_TLS_ROOT_CERT`, and `DB_CONNECT_TIMEOUT`:

```bash
export DATABASE_URL='postgres://agentvault:REPLACE@postgres.example:5432/agentvault'
export DB_TLS_MODE=verify-full
export DB_TLS_ROOT_CERT=/var/run/secrets/agent-vault/postgres-ca.crt
export DB_CONNECT_TIMEOUT=10s
agent-vault server
```

Do not place `DATABASE_URL`, database passwords, or encryption keys in images, ConfigMaps, process arguments, or committed TOML. Use a Kubernetes Secret or a secrets-store CSI projection.

## Size the connection pool

Each Agent Vault replica owns a separate Go connection pool. The maximum application demand is:

```text
aggregate Agent Vault connections = replicas × database.max_open_conns
```

For example, four replicas with `max_open_conns = 25` can consume 100 PostgreSQL sessions. That total must fit inside the database or pooler limit after reserving connections for administration, monitoring, migrations, failover overlap, and other applications. Lower the per-replica bound before scaling replicas. For larger fleets, place PgBouncer or the managed provider's transaction pooler between Agent Vault and PostgreSQL and budget both client and server-side pools.

`max_idle_conns` must not exceed `max_open_conns`. Agent Vault accepts 1–1000 open connections, a 30-second–24-hour connection lifetime, and a 1-second–1-minute connect timeout. These are validation limits, not sizing recommendations; database capacity remains the controlling bound.

## Kubernetes Secret

The fleet example expects the database URL, legacy master password, and PostgreSQL CA bundle in `agent-vault-secrets`:

```bash
kubectl -n agent-vault create secret generic agent-vault-secrets \
  --from-literal=database-url='postgres://agentvault:REPLACE@postgres.example:5432/agentvault' \
  --from-literal=master-password="$(openssl rand -hex 32)" \
  --from-file=postgres-ca.crt=/path/to/postgres-ca.crt
```

Prefer the configured AWS KMS or OpenBao Transit wrapper over the legacy master password for production fleets. See [runtime TOML configuration](/self-hosting/runtime-configuration) and [key recovery](/self-hosting/key-recovery).

## Fresh setup

1. Provision the dedicated role, database, schema, and CA bundle.
2. Create the Kubernetes Secret and mount the fleet TOML.
3. Start one replica and wait for startup migration and readiness to succeed.
4. Scale to the intended replica count within the calculated connection budget.
5. In legacy or hybrid authentication mode, create the initial owner. In SPIFFE-only mode, configure `auth.bootstrap_owner_ids` before first startup.

Every replica must use the same database, encryption-wrapper configuration, and SPIFFE trust policy.

## Migrating from SQLite

`migrate-db` copies the existing SQLite data to PostgreSQL in one transaction and does not modify the source database.

```bash
agent-vault migrate-db \
  --to 'postgres://agentvault:REPLACE@postgres.example:5432/agentvault' \
  --dry-run

agent-vault migrate-db \
  --to 'postgres://agentvault:REPLACE@postgres.example:5432/agentvault'
```

Configure `DB_TLS_MODE=verify-full` and `DB_TLS_ROOT_CERT` for the migration command, or put equivalent verified TLS parameters in the one-time destination URL. Use the same legacy master password or provider-backed key wrappers that protect the source data.

## Supported versions and rolling upgrades

Run the real PostgreSQL matrix locally with `make test-postgres-ha`; set `POSTGRES_VERSIONS="16 18"` to select a subset. The matrix covers concurrent startup, advisory locks, one-time SPIFFE bootstrap, refresh claims, forced connection loss, reconnect, and expired-lease takeover.

Schema migrations are forward-only. Every replica acquires the same database-scoped advisory lock before inspecting or updating the migration ledger, and waiting replicas do not become ready against a partial schema.

Keep replicas on the same Agent Vault version. Use `maxUnavailable: 0` and `maxSurge: 1`; wait for each new pod to become ready before continuing. Mix the previous and current versions only when release notes explicitly say their schema is backward-compatible. Do not roll an old binary back after a migration unless that release explicitly supports it; restore the pre-upgrade backup instead.

## Local Docker Compose

A local PostgreSQL container commonly uses an unencrypted connection:

```yaml
services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: agentvault
      POSTGRES_PASSWORD: dbpassword
      POSTGRES_DB: agentvault

  agent-vault:
    image: ghcr.io/stigenai/agent-vault:latest
    environment:
      DATABASE_URL: postgres://agentvault:dbpassword@postgres:5432/agentvault?sslmode=disable
      AGENT_VAULT_MASTER_PASSWORD: ${AGENT_VAULT_MASTER_PASSWORD}
    depends_on:
      - postgres
```

`sslmode=disable` is acceptable only for disposable local development on a trusted container network. Production deployments must use `verify-full` with an explicit trusted CA.

## Kubernetes probe contract

Use the dependency-specific endpoints from the fleet manifest:

| Endpoint | Purpose | External failures affect it? |
|---|---|---|
| `GET /health/startup` | Confirms the listener exists after migrations, SVID acquisition, DEK unwrap, and provider construction | Startup cannot listen until those steps succeed |
| `GET /health/ready` | Gates traffic on PostgreSQL, current SVID validity, and usable provider-backed credential caches | Yes; an expired last-known-good cache removes the pod from service |
| `GET /health/live` | Confirms the process and HTTP server can answer | No; database or provider outages do not trigger restarts |

The kubelet's probe timeout makes an unresponsive or deadlocked HTTP process fail liveness. A transient provider outage can fail readiness after the configured cache staleness window, but it never fails liveness and therefore does not create a destructive restart loop. `GET /health` remains a backward-compatible alias for readiness.

## Operational notes

- Readiness pings PostgreSQL with a bounded timeout. Failures return only safe component status; credentials and driver diagnostics are not exposed in the response.
- Startup connectivity and migration errors retain useful context while redacting URL passwords.
- The shared advisory lock prevents concurrent migration-ledger changes.
- Refresh work uses database leases so another replica takes over only after the claim expires.
- Database credentials remain independent from SPIFFE workload authentication and encryption-key wrapping.
